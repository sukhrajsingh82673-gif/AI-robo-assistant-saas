# OPEN_SOURCE_EVALUATION — ZONATA Agent Factory

**Status:** evidence-based, evaluated 2026-11-15. **Scope:** Brief Part 3 (candidates, comparison, licences, adopt/adapt/integrate/reject).

## 0. How to read the evidence

Every fact carries a tag. Anything without `[SRC]` or `[WEB]` must be re-verified by OpenCode at dependency-pin time (Phase 1 *licence gate*, see `OPENCODE_MASTER_IMPLEMENTATION_PROMPT.md`).

| Tag | Meaning |
|---|---|
| `[SRC]` | Read today from a shallow clone of the official repo (LICENSE file, `pyproject.toml`, `git log`, tags, source tree). The code was **read, never installed or run**. |
| `[WEB]` | Read today from a fetched web page (source named). |
| `[KNOWLEDGE]` | Maintainer knowledge before the June 2026 cutoff, **not re-verified today**. Treat as a hypothesis until the licence gate confirms it. |
| `[CLAIM]` | A statement from a project's own README that I did not independently execute (e.g. "209 tests pass"). |

Licences are checked **per component and per version**; ecosystems are not assumed to share one licence.

## 1. Headline findings

1. **Mozilla `agent-factory` is not a suitable foundation.** Last commit **2025-10-20** (about 13 months stale) `[SRC]`; it asks an LLM to emit *executable Python* (`imports`, `tools`, `structured_outputs`, `cli_args` fields in `AgentFactoryOutputs`) `[SRC]`; requires Python ≥ 3.13 and pins `any-agent==1.9.0` while `any-agent` is now 1.18.0 `[SRC]`; it has no tenant, approval, policy, registry or versioning concept. Its good ideas (NL→agent, generated evaluation cases, tested MCP-server catalogue) are worth copying; its code is not worth depending on.
2. **`bagalsharad/agent_factory` is the closest architectural match, but is alpha.** It treats agents as **declarative, versioned specs** (no model-generated code runs in the backend), uses **LangGraph**, has a policy engine outside the model, approvals with separation of duties, evaluation-based release gates, a threat model, and 14 ADRs `[SRC]`. It is also **very new**: 17 commits between 2026-11-01 and 2026-11-04, one codebase of ≈20.6k Python lines, version 0.1.0 `[SRC]`; its repository contains `AGENT_FACTORY_MASTER_BUILD_PROMPT.md`, `CLAUDE.md` and `AGENTS.md`, i.e. it was built with a coding agent `[SRC]`. Its README says 209 backend tests pass `[CLAIM]`. **Decision: ADAPT** — reuse the *spec model, validator, templates, evaluation taxonomy and gate logic* as reviewed, vendored, attributed code (Apache-2.0); **do not** adopt its own governance, auth, queue or UI, because ZONATA already owns those and duplicating them would create a second sovereign authority.
3. **LangGraph stays the single runtime.** `langgraph 1.2.22` (2026-11-13), MIT `[SRC]`. The *library* is MIT; **LangSmith / LangGraph Server (Agent Server) is proprietary** and billed per run `[WEB: docs.langchain.com/langsmith/faq]` — the factory must depend only on the library and the Postgres checkpointer, never on the hosted platform.
4. **Three licence/supply red flags in the existing stack** (all verified today, details in §4): **MinIO community repo was archived on 2026-04-25** (no more security patches) `[WEB]`; **HashiCorp Vault is BSL 1.1** (OpenBao is the MPL-2.0 drop-in fork) `[WEB]`; **promptfoo is being acquired by OpenAI** (MIT today, governance risk) `[WEB]`. Human decisions required (see `GAP_AND_RISK_REGISTER.md`).
5. **Do not add CrewAI or Agno as runtimes.** Both are actively maintained and permissively licensed (MIT / Apache-2.0 `[SRC]`), but each would introduce a second orchestration model beside LangGraph, plus default telemetry that must be disabled (`CREWAI_DISABLE_TELEMETRY`/`OTEL_SDK_DISABLED`, `AGNO_TELEMETRY=false` `[SRC]`). The factory emits **one framework-neutral spec compiled to LangGraph**. Optional *import adapters* (read an external CrewAI/Agno definition and convert it to a spec) are deferred to after the pilot.

## 5. Final technology selection (Brief §3.3)

**Category 1 — core technologies to integrate**
LangGraph (existing runtime, library only) · Postgres/Neon with RLS (+ pgvector if no vector store exists) · Temporal via `OrchestratorPort` (existing) with `DbQueueOrchestrator` fallback · existing ZONATA PolicyEngine, AuthorityGateway, ApprovalEngine, EvidenceLedger, KillSwitchMatrix, OpenFGA, Keycloak, Vault/OpenBao via ports · Letta (existing memory) · existing MCP and A2A layers · OpenTelemetry + Langfuse (existing) · Pydantic v2 + JSON Schema for specs · Ed25519 signing (`cryptography`) · gitleaks, Bandit, Ruff, pip-audit, OSV-Scanner, Syft · S3 API storage behind a port · **vendored, attributed modules from bagalsharad/agent_factory** (spec, validator, templates, eval checks, gate logic) after review.

**Category 2 — optional adapters (only where needed, feature-flagged)**
OpenHands "Tool Smith" (T2 sandbox only) · Semgrep (own rules) · promptfoo / DeepEval / garak / PyRIT as additional evaluators (pinned) · gVisor / Firecracker / Kata sandboxes (paid/VM hosts) · Sigstore cosign (container images) · CrewAI/Agno **import** converters (post-pilot) · Qdrant (if pgvector is insufficient).

**Category 3 — do not adopt (duplicate or unsuitable)**
Mozilla agent-factory (stale; code-generation model) · CrewAI and Agno as runtimes · any-agent/any-llm (ZONATA model gateway already exists) · Google ADK, OpenAI Agents SDK, Microsoft Agent Framework/AutoGen, Pydantic AI, smolagents as runtimes · LangGraph Server/LangSmith Deployment · `langgraph-supervisor` as a dependency (stale since 2026-07-14; trivial to implement in-house) · OPA/Cedar/Casbin (PolicyEngine + OpenFGA already decide) · new MinIO deployments · a second workflow engine, a second identity provider, or a second audit store.
